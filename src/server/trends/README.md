# Daily recipe radar

Current workflow (migrations 0018–0019): `/admin/automation` has one owner switch for daily research and automatic publication of a new verified social trend at 06:00 Europe/Warsaw. Manual recipes publish only through the editor’s Publish button. Migration 0020 records permanent editorial takeover by recipe ID after manual edits, content approval, repairs or Studio admissions; later worker writes and diagnostic refreshes cannot restore automatic ownership. The publisher accepts only the preceding day’s ordinary daily search, system-approved cooking content and complete registered media. Research fallback inspirations remain drafts. Ingredients are prepared before steps; the final dish photo is last. The old reviewed FIFO, exact-date manual plans and control-run enablement requirements below describe preserved historical mechanisms and do not govern current publication. See `docs/trends-runbook.md` for the operating procedure.

`GET /api/cron/trends` is protected with a constant-time `CRON_SECRET` comparison. Vercel calls it at 12:00 UTC; database settings default to disabled. The Warsaw calendar date is unique across ordinary daily and control runs, so cron retries, daylight saving changes and repeated clicks cannot produce a second automatic daily dish.

The active owner explicitly enables daily research and verified-trend publication with one switch. Required services, budget, exact revisions and complete cooking text/media are checked during actual preparation. A separate control run is no longer required for enablement. Historical control fingerprints remain diagnostic metadata and never grant publication permission. `editorial_content_approval` records system approval only for new verified daily trends; it never fabricates human review.

An authenticated editor can explicitly press the control button again after a confirmed, settled, zero-cost search rejection. Admission keeps the same date and run ID, reserves the model-specific search allowance again and increments the workflow generation. This exception requires a failed control with a claimed and finished search, no provider receipt, no draft, candidates, child jobs or remaining media packet. Concurrent clicks dispatch one new generation. Daily cron admission, uncertain requests and any incurred or unsettled charge never take this path; there is no automatic paid retry.

An owner can explicitly authorize an additional paid manual run on the current Warsaw date through `action: 'manual', requestKey: <UUID>`. It creates a separate control record with the real calendar date and preserves all previous run costs, evidence and results. A stored owner account is required; admins, the scoped worker and cron cannot admit it. The same UUID, including concurrent or later replay, returns the original record with `created: false` and cannot dispatch a second request. It never restarts or overwrites that record. A new UUID still requires configured services, available budget and no active or uncertain run. Manual runs use the same recipe selection strategy, budget, full-photo control and publication gates, and do not enable scheduling automatically. Their DTO contains `manual: true`, without exposing the private request UUID. Ordinary daily/control admission ignores these records when checking the unique base run for the date.

Search uses its own `AI_TREND_MODEL`, defaulting to `gpt-6.1-sol`, independently of the existing recipe and photography models. Admission persists the search model, so changing configuration never changes the accounting for an existing receipt. Legacy rows without a saved model use their original `gpt-6-astra` pricing. Responses `web_search` has explicit social/culinary domain filters, six maximum tool calls, 7,000 maximum output tokens, low search context and no paid POST retry. Discovery first researches likely dishes without literal year/month terms, date operators or mandatory single-site queries, then looks for fresh evidence; the verifier still requires actual publication dates within 14 days. Up to 12 incomplete candidates and 12 approved source URLs from the previous 14 days provide context, never qualifying evidence by themselves.

The search reservation is a conservative stress estimate: $40 for Sol and $200 for Astra, allowing seven full-context model passes, the long-context cache-write rate, maximum output and six tool fees. It is a reservation, not an expected daily charge or a provider-enforced spending cap. An Astra search cannot be newly admitted under the default $150 monthly feature limit. Verified token usage and $0.01 per web-search call release unused reservation; inputs above 272,000 tokens use the documented 2× input/cache and 1.5× output pricing. Missing usage retains its reservation even if a response is terminal. Existing historical reservations and costs remain unchanged.

Each completed search stores private diagnostics: model, actual tool-call count, query strings, returned URL count, candidate count, submitted and retained evidence counts, and stable verification/ranking issue codes. Every newly completed search ends with `outcome: selected` and exactly one selected recipe. Optional `discoveryOutcome` separately records empty discovery, unverified sources, insufficient evidence or a qualifying trend, so a recipe selection does not conceal missing trend evidence. Legacy outcomes remain readable. Ranking failures such as stale dates contribute to the final diagnostics rather than disappearing with rejected evidence. The panel shows settled usage separately from outstanding search and whole-packet reservations.

The historical protection for two consecutive accepted, settled searches ending without a candidate remains under the same budget lock used for admission. New completed searches select a recipe and do not produce `no_candidate`; changing strategy does not clear an existing pause or enable scheduling. Control and daily runs both count; a selected dish breaks the streak. A third cron creates no run and reserves no money. The owner must review diagnostics and explicitly acknowledge the current `autoPauseToken` before enabling again. The token identifies the exact two triggering runs, so a stale panel cannot clear a newer pause. Reviewed runs are excluded from the next streak; successful work never enables the scheduler automatically. A manual control remains available on a new Warsaw calendar date.

`refreshTrendDiagnostics(id, actor)` can backfill a legacy receipt using authenticated, read-only provider GETs. It requires a finished receipt and updates only diagnostic JSON after checking that the run generation, receipt, status and saved model still match. It cannot submit a paid request, re-rank historical candidates, change the selected dish, alter costs, or edit recipe/publication data.

Only URLs actually returned by the search tool or citations can qualify. A read-only verifier checks at most 24 approved HTTPS pages, four concurrently, with a six-second timeout and 512 KB decoded-body limit. Redirects are manual, limited to two, and remain on the approved host list. No cookies, credentials or page scripts are used. A literal short quote and matching publication metadata date must be present. Blocked sources are marked unavailable, and unverifiable evidence is excluded.

Confirmed trend ranking uses the last 14 days, three independent source identities, one verified social creator and a literal quote expressing current interest. Web identity comes from its domain; creator identity comes from the URL, rather than a model-authored publisher string. Post links without a verifiable creator remain context and contribute no independent origin. Alias matches merge before ranking; existing drafts/publications and previous selected aliases prevent duplication. Unknown overlap excludes a lead from automatic preparation and the selector moves to the next option.

Every daily, control and additional manual search now also aims for a catalogue of roughly 50% meat/fish dishes, 25% vegetarian and 25% vegan. Counts use only current active publication snapshots, once per recipe; historical versions, trash, archived recipes and discarded drafts cannot distort them. A rolling window of the latest twelve publications and retained, prepared drafts prevents a long one-sided catch-up after an uneven historical catalogue. When a side reaches 60% of that recent window, the next choice prefers the other side; within the plant side the less represented vegan/vegetarian category is preferred. This is a selection target, never permission to change a dish's actual ingredients or to mislabel its diet.

Discovery receives these counts and the desired category before its one bounded search. It actively seeks practical complete dishes for the missing group, rather than filling the vegan/vegetarian share only with desserts and garnishes. New discovery output includes a nullable diet based on the intended base ingredients; older stored receipts with no category remain readable. Unknown or contradictory vegetable-led titles never establish vegan suitability. Final recipe generation checks the actual full ingredients against any captured target.

Within the target category the selector prefers a new confirmed trend, then a usable researched inspiration. If discovery contains no safe candidate of that category, it checks the local seasonal bank, which includes meat, fish, vegetarian and vegan ideas. Only after the target reserve is exhausted does it fall back to the best available new idea of another category. The selected candidate privately records `dietSelection` with target, actual intended category, current/recent counts, a reason and a fallback flag. Fallback neither submits another paid search nor stops daily preparation. With the entire bank exhausted, an existing catalog recipe is reused. Research inspirations do not require a minimum number of verified trend sources. Missing, stale or unavailable evidence stays excluded from verified sources and its diagnostic reasons are preserved. Seasonal choices contain local cooking context and no invented URLs, dates, creators or popularity claims. Duplicate and ambiguous research leads are skipped, and seasonal choices check the same catalog/selected history before choosing a new dish.

`TrendRun.selectionBasis` records `trend`, historical `editor`, `inspiration`, `seasonal` or `catalog`. Automatic candidates also save `automaticSelection: { basis: research | seasonal | catalog, reason }`. Only an eligible candidate without an editor choice or automatic selection can receive the public “Popularne teraz” marker and its freshness date. Selecting a recipe does not relax trend evidence requirements or publish anything.

A catalog revisit attaches the existing recipe ID and enters `awaiting_review`, rather than creating a duplicate draft or submitting new text/photo requests. It does not renew popularity or certify a control. New research/seasonal inspirations stop after cooking text and remain drafts until a human accepts the content; they are not automatically photographed or published. Selection guarantees one recipe for a successfully completed search; admission, provider failures, unresolved receipts, exhausted budget and editorial rejection remain explicit operational states.

`finishTrendSearchFailure` also preserves a recipe selection when the search service rejects or fails a confirmed request, or returns an unusable structure. It chooses a seasonal candidate and continues the normal preparation workflow without another search POST. When receipt acceptance or completion is uncertain, including a timeout, it still selects a seasonal candidate and saves its draft, but leaves the run `uncertain`, keeps the outstanding search reservation and submits no new text or photography jobs until the existing request is explained. Recipe selection never conceals an unresolved paid request or triggers its automatic resubmission.

An owner can `reverify` a legacy `no_candidate` result by reading its existing paid receipt, rechecking evidence and applying the current selector. This does not submit another paid search. New preparation still requires available budget and services; the recorded search charges are retained. This action is distinct from diagnostic-only `refreshTrendDiagnostics`.

The scoped `trend_worker` has no user account and can only create and apply its own stored run's unapproved draft. Text uses the normal configured provider. Before the first photograph, the entire undispatched media packet is reserved under the radar's $150 monthly limit. Total radar commitment is search cost plus unused packet reservation plus child-job commitments, counted once; manual pilot limits exclude these child jobs, while global provider concurrency still applies.

After content approval, the entire missing photo packet is reserved. Ingredients are prepared first, steps second, and the final dish photo last. Each completed photograph is saved before the next slot; a failed or uncertain slot stops later spending. The final dish uses the full accepted cooking concept. Any manual content revision prevents automatic application. Pauses preserve paid results and reservations, resume confirmed jobs without resubmission, and increment a generation fence so an obsolete worker cannot change the new run. An uncertain search without a provider ID cannot be repeated; rejecting the run unlocks the next day while its unresolved cost remains counted.

Receipt polling uses durable Workflow `sleep`, never a long function timer. The first delays are 10, 10, 20, 20, 30, 30, 60 and 60 seconds, followed by five-minute intervals. At most 20 reads wait 64 minutes per existing provider request; search uses at most 14 reads over 34 minutes. Completion stops further sleeps immediately. Paid submission remains a single POST with zero automatic retries.

The hard packet ceiling is 40 photographs in total: hero plus all ingredient and step images. The usual text brief requests at most 12 ingredients and 8 steps, but the event-budget calculation covers the enforced larger ceiling, plus one text job. The regression test includes all allowed read retries, the 60 admission retries, six billing rounds and durable sleep events. Its complete logical run stays below 20,000 events and 10,000 steps, leaving headroom under the [Vercel limit of 25,000 events](https://vercel.com/docs/workflows/pricing#workflow-run-limits). Keep these shared ceilings in `src/lib/trend-polling.ts` aligned when changing packet size or retry policies.

Manual `approve_and_publish` requires the exact revision and all six explicit review checks. It accepts pending alternatives, validates the complete accepted copy and atomically writes the immutable manual publication, recipe revision, audit/outbox and radar publication state. The worker cannot call this path.
